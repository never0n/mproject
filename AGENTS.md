# AGENTS.md --- Codex rules for Desctop_MMO

## Перед любой работой

Для game-design задачи сначала прочитай: 1. `PROJECT_CONTEXT.md`; 2.
`game-design/00_GAME_MAP.md`; 3. `game-design/01_CORE_PRINCIPLES.md`; 4.
релевантные файлы подсистемы; 5. `game-design/90_OPEN_QUESTIONS.md`.

При изменении канона используй `game-design/99_DECISION_LOG.md`.

Перед изменением кода дополнительно изучи реальную затрагиваемую кодовую
базу, зависимости и тесты. Не делай вывод о текущей реализации только по
design-документам.

## Source of Truth

Приоритет: 1. актуальный `game-design/`; 2. `PROJECT_CONTEXT.md`; 3.
`game-design/99_DECISION_LOG.md` как история; 4. старые документы/чаты
--- только исторический материал.

Новое явное решение автора имеет приоритет над старым. Существенно
изменённое старое решение фиксируй в Decision Log.

## Статусы

Используй строго: - `[CANON]` --- явно утверждено автором; -
`[TENTATIVE]` --- направление принято, детали не финальны; - `[OPEN]`
--- решения нет; - `[DEFERRED]` --- сознательно отложено; - `[PROPOSAL]`
--- идея ассистента/Codex, которую автор не утвердил.

**Никогда не повышай `[PROPOSAL]` до `[CANON]` самостоятельно.**

## Design interview

Если пользователь просит продолжить обсуждение дизайна: - задавай
**ровно один вопрос за раз**; - сначала проверь, нет ли ответа в Source
of Truth; - не задавай вопрос, если ответ прямо следует из core
principles; - не задавай вопросы вида «физический ли X?», если X
подпадает под принцип физического мира; - не задавай автору вопросы,
которые по концепции должны решать будущие фракции/игроки; - предпочитай
фундаментальные неизвестные, влияющие на несколько систем; - не уходи в
баланс конкретных чисел раньше принципа; - если пользователь просит
мнение, можно критиковать и предлагать варианты, но отделяй предложение
от канона; - если факт потерян и его нет в Source of Truth, не угадывай.

После явного решения: 1. обнови релевантный MD; 2. закрой/измени
соответствующий `[OPEN]`; 3. при существенном изменении добавь краткую
запись в `99_DECISION_LOG.md`; 4. затем переходи к следующему вопросу.

## Не кодить без запроса

Во время design-интервью **не начинай реализацию, рефакторинг или
массовое удаление кода**, пока пользователь явно не попросил перейти к
коду.

Не превращай каждое design-решение в немедленную задачу разработки.

## Работа с существующим кодом

Когда пользователь просит redesign/implementation: - сначала сделай
inventory затрагиваемых модулей; - найди зависимости legacy-рас, NPC,
старой progression и других старых систем; - мигрируй поэтапно; - не
удаляй работающий фундамент боя только потому, что финальная боёвка ещё
не определена; - сохраняй полезные технические подсистемы, если они не
противоречат новой концепции; - сложные поздние системы не реализуй
преждевременно; - различай **«нужно заложить архитектурно сейчас»** и
**«нужно реализовать сейчас»**; - после разумных этапов проект должен
оставаться собираемым и тестируемым.

## Архитектурный принцип

Предпочитай общие primitives вместо жёстко прошитых социальных ролей.

Примеры: - ownership/access/key primitives вместо отдельной системы
«банк»; - physical item/container/transport primitives вместо глобальной
телепортации товаров; - faction/territory/siege primitives вместо набора
заранее заданных типов государств; - document/signature primitives
вместо автоматического универсального суда; - activity/XP/skill
primitives вместо жёстких классов профессий.

Не создавать специальную систему, если нужное поведение естественно
возникает из уже существующих общих механик.

## Физичность мира

Считать базовым правилом: - материальные товары существуют физически; -
транспортировка физическая; - деньги физические; - хранилища
физические; - документы физические; - производимые объекты создаются
игроками; - собственность и доступ опираются на механики мира.

Не трать интервью на повторную проверку этого правила для каждого
предмета.

## Социальный слой

Не автоматизируй без причины: - мораль; - глобальную репутацию; -
политический строй; - социальное доверие; - наследование; - суд; -
трудовые споры; - выполнение контрактов.

Это пространство emergent society.

Автоматизация допустима для технической рутины, если без неё система
становится неинтересной бухгалтерией, но такое решение должно быть явно
зафиксировано.

## Реализм

Не предлагай реализм как самоцель.

Перед добавлением симуляционной детали спроси: 1. создаёт ли она
решения? 2. создаёт ли она риск/экономику/социальное взаимодействие? 3.
или только добавляет рутину?

Если только рутину --- по умолчанию не добавлять.

## Работа с неопределённостью

Если пользователь говорит: - «да, именно так» → можно фиксировать
`[CANON]`; - «скорее так», «наверное», «можно попробовать» →
`[TENTATIVE]`; - «подумаем потом» → `[DEFERRED]`; - решения нет →
`[OPEN]`.

Если в одной реплике пользователь сначала предлагает вариант, затем
отказывается от него, фиксируй **последнюю ясную позицию**.

## Защита от потери контекста

Никогда не полагайся только на память текущего диалога для уже
обсуждённых систем.

Перед фундаментальным вопросом выполни поиск по `game-design/`.

Если новый ответ меняет несколько систем, обнови все затронутые файлы
либо добавь явные cross-links/TODO, чтобы зависимость не потерялась.

## Коммуникация

Пользователь предпочитает: - прямые ответы; - минимум повторов; - один
вопрос за раз; - отсутствие длинных вступлений; - отсутствие повторного
пересказа его ответа без необходимости; - критику, когда есть реальная
design-проблема, а не автоматическое согласие.

Не превращай интервью в анкету из десятков вопросов за один ответ.

## Git

При работе с кодом/документами: - сначала `git status` / изучение
diff; - делать логически цельные изменения; - не смешивать несвязанные
массовые изменения; - не делать destructive Git operations без явной
необходимости; - не пушить/тегировать/релизить без явного запроса
пользователя.

## Цель текущей фазы

Сейчас приоритет: 1. стабилизировать Source of Truth; 2. закончить
design excavation фундаментальных систем; 3. построить dependency map;
4. определить architectural foundation; 5. создать реалистичный
migration/implementation roadmap; 6. только затем последовательно
переделывать существующий проект.
