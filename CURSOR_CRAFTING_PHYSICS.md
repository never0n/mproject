## 3. Границы первого внедрения

Сначала один материал C90700 и форма с одним последовательным путём
заливки: хвостовик, клинок, остриё. Игрок редактирует продольный профиль,
длины, ширины, толщину и параметры процесса; это не три фиксированные
кнопки «короткий/обычный/длинный». Ограниченный редактор профиля —
только промежуточный технический срез. После уточнения автора он
не является достаточным выполнением задания на редактор: см. раздел 8.1.

Общие сущности называй Material, Geometry, Process, Blueprint, Result;
меч — проверочный сценарий, а не специальная физика для одного kind.
Не обещай произвольное 3D-литьё на основе одномерного решателя.
Разветвлённую/полую/неподдерживаемую форму явно отклоняй до расходования
материалов. Позднее её потребует отдельный решатель графа/объёма.

Не добавляй износ оружия, разбор готовых вещей на материалы, случайный
процент качества или новую формулу боя. Таланты ограничивают доступные
параметры, не подменяют физику случайным успехом. Не позволяй называть
готовое изделие «сырьём», чтобы обходить запрет разборки.

## 4. Данные и разделение ответственности

Выдели чистый численный модуль без БД, UI и сетевых обращений, например
`crates/server/src/crafting_physics/`. Если повторное использование
потребует отдельного crate, обоснуй это фактическими зависимостями.
В протоколе — сериализуемые команды и результаты, не серверная оркестрация.

Минимальные структуры:

- `MaterialDefinition`: ID/версия, плотности по принятой фазовой модели,
  c, L, solidus/liquidus, μ, k, d, коэффициент Kozeny, происхождение данных.
- `DesignGeometry`: профиль и единицы, система координат, припуск,
  вход, поддерживаемая топология. Проверенный сервером производный mesh.
- `ProcessRecipe`: масса загрузки, действия/их физические времена,
  мощность, температуры, режим напора, условия формы, обработка.
- `CraftSession`: владелец/станция, ID входных вещей, зарезервированная
  масса, состояние процесса, revision, последовательность команд,
  версия модели и материала, физическое время, состояние решателя.
- `CellState`: объём, занятый объём, масса, энергия, температура,
  доля жидкости, реальные смоченные стенки, связи с соседями.
- `CraftResult`: фактическая геометрия, материал и масса, центр масс,
  тензор/оси инерции, дефекты с координатами и временем, версия расчёта.
- `Blueprint`: неизменяемая версия геометрии и требований процесса,
  версии solver/material и явный масштаб времени. Личное знание и
  физический лист ссылаются на неё; бумага остаётся физической вещью.

Создай типизированные записи/таблицы, а не новые значения `plan_*`
в характеристиках и не ещё одну упаковку в `Stack.lock`.
Свяжи индивидуальные свойства с постоянным ID предмета. При переносе,
продаже, экипировке, смерти и перезапуске они не должны исчезать.
Разные изделия не сливаются в одну стопку по совпадению kind.
Вес в инвентаре берётся из экземпляра, с прежним fallback для старых вещей.

SI внутри решателя: м, м², м³, кг, с, Па, Дж; температуру можно хранить
в °C при явно заданной относительной энтальпии. UI переводит мм/см³.
Массу складского сырья храни в фиксированной единице учёта; перевод
в f64 для расчёта не должен создавать ресурсы из округлений.

## 5. Формулы первой версии

Полные исходные данные и оговорки — в численном примере; не копируй
его прежние, явно отменённые выводы про недолив 14,1 см.

### Нагрев и фазы

Для эталонного материала:

```text
Ts = 831 °C; Tl = 999 °C
c = 380 J/(kg K); L = 180000 J/kg
rho_liquid = 8000 kg/m³; rho_cold = 8770 kg/m³
f(T) = clamp((T - Ts)/(Tl - Ts), 0, 1)
e(T) = c (T - 20) + L f(T)
E = m e(T)
```

Инвертируй e(T) кусочно: твёрдое тело, диапазон фазового перехода,
жидкость. В переходе c_eff = c + L/(Tl-Ts). Добавляй/отнимай энергию,
а не произвольные градусы. Для нагрева dE/dt = P_net; если считаешь
потери печи отдельно, не вычитай их второй раз из уже чистой мощности.

Контроль: 1,8 кг от 20 до 1070 °C требуют 1042,2 кДж; при P_net=1000 Вт
это 1042,2 с. Потеря 30 °C всей жидкой загрузкой — 20,52 кДж.
Не вводи произвольное правило «при переносе всегда минус 30» в общий
движок: это фиксированное условие эталона, отдельно от модели переноса.

### Проницаемость и поток

```text
mu = 0.004 Pa s; d = 100e-6 m; C_K = 180
K(f) = d² f³ / (C_K (1-f)²)
R_mushy_i = mu * occupied_length_i / (K_i * section_i)
R = sum(R_liquid_i + R_mushy_i)
delta_p = rho_liquid * g * H
B = rho_liquid / (2 * Cd² * gate_area²)
Q = 2 * delta_p / (R + sqrt(R² + 4 * B * delta_p))
```

Для эталона H=0,15 м, Cd=0,65, g=9,81; delta_p=11772 Па.
`R_liquid` считай по формуле прямоугольного канала из численного примера:

```text
a = max(width, thickness); b = min(width, thickness)
F = 1 - 192*b/(pi^5*a) * sum(tanh(n*pi*a/(2*b))/n^5)
R_liquid = 12*mu*occupied_length / (a*b^3*F)
# сумма по нечётным n=1..59
```

f=1: R_mushy=0; f=0 в занятой ячейке: этот путь непроходим.
Обработай пределы отдельно, без NaN/Infinity в сохранении. Не используй
f≤0,5 или минимальный расход как физический критерий закупорки.
Пустая ячейка не является замёрзшей. У фронта сопротивление соответствует
занятой длине. Нулевой напор даёт Q=0; обратное течение в первом срезе
не поддерживается и не должно появляться случайно из отрицательного ввода.

### Тепло во время заполнения

```text
e_liquid(T) = c*(T-20) + L
full_cell:
  dE_i/dt = rho*Q*(e_liquid(T_upstream)-e_liquid(T_i))
             - h*A_wet_i*(T_i-T_mold) + sum(G_ij*(T_j-T_i))
front_cell:
  dm_i/dt = rho*Q
  dE_i/dt = rho*Q*e_liquid(T_upstream)
             - h*A_wet_i*(T_i-T_mold) + sum(G_ij*(T_j-T_i))
G_ij = k*min(section_i, section_j)/distance_between_wet_centers
```

Эталон: h=60 W/(m² K), T_mold=200 °C, k=70 W/(m K).
Переносится энтальпия жидкой фазы, а не средняя энтальпия неподвижного
твёрдого каркаса. Общие тепловые потоки между соседями сокращаются.
Внутренние грани сетки не охлаждаются как стенки формы. Контактная
площадь фронтальной ячейки растёт вместе с заполнением.

Порядок шага: T/f из массы и энергии → сопротивления → Q → устойчивый dt
→ консервативное обновление энергии/массы → продвижение фронта → события.
Граница ячейки/действие игрока/исчерпание источника должны завершать шаг
точно. Отдельно обрабатывай пустую начальную ячейку без деления на массу.
Для явной схемы ограничь перенос четвертью занятой массы, проводимость
шагом 0,2*m*c/sum(G), дополнительно заданным dt_max. Проверяй остаток
массы источника. При исчерпании источника сохраняй уже заполненное.

### Охлаждение и последующие операции

После конца заливки продолжай с рассчитанного поля E/T, не сбрасывай
все ячейки на 1040 °C. При Q=0 остаются теплоотдача и теплопроводность.
Усреднённая формула для изолированного теста:

```text
delta_t = m*c_eff/(h*A) * ln((T_start-T_env)/(T_end-T_env))
```

Числа 130,87 с до полного затвердевания и 384,18 с до 300 °C из
документа относятся к отдельному равномерному телу массой 1,428633 кг.
Не требуй этих чисел от пространственной модели после реальной заливки.

При заполнении плотность постоянна, усадочная подпитка этим решателем
не вычисляется. Полная полость содержит 1,362728 кг жидкости;
нельзя выдать плотную холодную заготовку 1,428633 кг без дополнительных
0,065905 кг. Раздели cavity-fill и feeding в данных/результатах.
В первом интегрированном сценарии допустим явно обозначенный режим
идеального доступного питателя: резервировать и реально списывать
добавочную массу; не утверждать, что шейка проверена физически.
Без него сохранять фактическую массу, дефицит объёма и статус
`feeding_unresolved`, не выдумывать координаты усадочных пор.

Для обработки уменьши реальную геометрию и массу снятого материала.
Для эталонных скосов A(x)=w(x)*(3*t+e_edge)/4, t=6 мм, e_edge=0,1 мм;
центральная половина ширины остаётся полной толщины. Расход шлифовки
не означает разрешения разбирать готовые предметы обратно на сырьё.
Для полной плотной заготовки: металл после обработки 1,108473 кг;
с рукоятью 0,18 кг — 1,288473 кг. При недоливе пересчитывать по факту.

Центр масс: sum(m_i*r_i)/sum(m_i). Инерция: локальная инерция каждого
объёма плюс перенос оси; для сборки учитывать детали и крепление.
Эталонный центр масс x=0,203258 м от основания, инерция относительно
хвата x=-0,06 м по нормали к плоскости клинка 0,148953 кг·м².
E≈103 ГПа, предел текучести≈150 МПа и HB≈80 — входные справочные
ориентиры, не вычисленные из охлаждения свойства. Не выдавать их за
результат микроструктурного расчёта и не превращать в урон без отдельного
решения. Существующую боёвку сохранить; до согласования адаптера новый
результат может оставаться физической заготовкой, не боевым предметом.

## 6. Эталонная геометрия и критерии численного результата

Холодный чертёж: хвостовик x=-0,12..0 м шириной 0,02 м;
клинок x=0..0,60 м с w=0,05-x/30; остриё x=0,60..0,65 м
с w=0,03*(0,65-x)/0,05. Толщина всюду 0,006 м. Размеры формы
умножены на s=1,015; объём 170,341007 см³. Координаты отчётов —
в исходном чертеже до припуска, это должно быть явно записано.

Вход эталона — диафрагма нулевой длины, источник 1040 °C,
постоянный напор и свободный выход воздуха. Отсчёт от входа в хвостовик.
Каналы и питатель не входят в время заполнения полости.
Нельзя выдавать этот тест за моделирование промерзания длинного литника.

Ориентиры для сетки 2,5 мм, dt_max=0,005 с:

- Вход 25 мм²: заполнение около 6,13 с; минимум T около 1004 °C;
  все ячейки заполнены, твёрдой пробки до конца заливки нет.
- Вход 2 мм²: на 20 с Q≈2,192 см³/с, фронт≈9,69 см;
  на 40 с Q≈1,518, фронт≈23,71 см; на 70 с Q≈0,156,
  фронт≈31,49 см; на 100 с Q≈0,0113, фронт≈32,17 см.
- Первая твёрдая пробка около 137,41 с, x=9,50..9,75 см.
  Заполнено около 105,26 см³; фронт≈32,21 см, недолив≈64,08 см³.
- Сетка 1,25 мм, dt_max=0,0025 с: 137,23 с; пробка 9,50..9,625 см;
  фронт 32,14 см, заполнено 105,07 см³.

Начальные допустимые интервалы при воспроизведении именно этих условий:
быстрый вход 6,1..6,2 с; узкий вход пробка 136..139 с, её положение
9..10,5 см, фронт 31,5..33 см. Это численные регрессионные ориентиры,
не точность физики. Если результат не попал — исследуй единицы,
стенки, тепло, геометрию и интегратор. Не подгоняй d/h под тест.
Сохрани входные fixture и исполняемый генератор результатов в репозитории;
не ссылайся на временные файлы предыдущего обсуждения как зависимость.

Характеристики d/h некалиброваны. Чувствительность d=50/100/200 мкм
на сетке 5 мм даёт фронты примерно 21,86/32,35/45,81 см.
Точные координаты дефекта для реального сплава пока неизвестны.

## 7. Серверная сессия, транзакции и воспроизводимость

Команды должны выражать действия: сохранить проект, загрузить материал,
начать нагрев, изменить доступный режим, залить, завершить/прервать
операцию, обработать, получить результат. Конкретные названия условные.
Сервер проверяет доступ к станции, расстояние, состояние персонажа,
талант, наличие и массу сырья. Клиент не присылает итоговую температуру,
качество или готовые свойства как доверенные данные.

Проектирование без производственного действия не должно автоматически
сжигать единицу материала как нынешняя заглушка `design`.
При старте реального процесса атомарно перемести/зарезервируй сырьё
в физической сессии; исключи его одновременную продажу и использование.
При завершении атомарно запиши результат и выдачу. Уникальный operation ID
и revision обеспечивают идемпотентность: повтор пакета, reconnect или
повторный запуск worker не дают второй предмет/XP и не списывают сырьё дважды.
При заполненной сумке предмет остаётся на станции/в разрешённом физическом
контейнере, не исчезает и не дублируется. Ошибка БД до commit не меняет мир.

Не держи глобальную блокировку симуляции и транзакцию БД во время
численного расчёта. Снимок валидированных входов → ограниченный worker
→ короткий commit с проверкой актуальной revision. Резервирование должно
сохраняться независимо от падения worker; восстановление продолжает
процесс из checkpoint или детерминированно воспроизводит его журнал.

Физическое время отделено от сетевых кадров и времени CPU.
Коэффициент ускорения игрового времени конфигурируем и версионируем;
не ускорять одни только теплопотери. Простой сервера в первом срезе
явно приостанавливает расчёт, продолжение идёт от сохранённого времени.
Отключение клиента не возвращает уже расплавленное сырьё.
Политику ручных действий после отключения зафиксируй отдельно: новых
действий нет, ранее начатый физический процесс продолжает свою модель.

Одинаковые нормализованные входы, версии и журнал действий дают тот же
результат независимо от частоты кадров/пакетов. Стабильный порядок ячеек,
явные dt и округления; не обещать битовую одинаковость f64 между любыми
платформами без проверки. Зафиксируй поддерживаемый серверный runtime,
формат сохраняемых результатов и регрессионные проверки повторяемости.
Обновление solver не пересчитывает уже существующие предметы молча.
Старый чертёж сохраняет версию исполнения либо получает явную миграцию,
а не незаметно новый результат по тем же требованиям.

## 8. Клиент и реальные дефекты

Редактор показывает профиль с размерами и физическую форму; игрок
меняет контрольные точки/толщину в поддерживаемой области. Сервер
повторно валидирует её. Нельзя пересылать неограниченный mesh напрямую
в решатель. Предварительный просмотр отделён от фактического опыта;
итоговые свойства приходят после производственных действий.

В процессе показывай металл, нагрев, заливку и охлаждение с понятными
параметрами. После опыта — фактически полученную форму, массу и дефекты.
Для эталона визуально должна отсутствовать недолитая часть, а не только
появляться надпись «качество 62%» над целым мечом. Строй mesh результата
из того же заполнения, что использует сервер; нормали, коллизия и масштаб
должны соответствовать видимой геометрии.

`misrun` описывает незаполненный объём; `solidified_feed_path` — причину
с временем и ячейкой пробки. Это разные координаты. Не называть это
холодным спаем: встреча фронтов не решается. Не генерировать газовые поры,
трещины или свойства зёрен, для которых нет модели.
Если игрок прекратил лить раньше пробки, сохраняй недолив с причиной
прекращения подачи. Если исчерпано сырьё — отдельная причина.
Численный сбой/превышение вычислительного бюджета — технический статус,
не физический брак и не случайное уничтожение материалов.

Зафиксируй ограничения на число точек, размер сетки, шаги, длительность
и конкурентные задачи. Проверяй конечность чисел, положительность сечений,
диапазоны температур, массы и площади входа, самопересечения и единицы.
Измерь время и память эталона; тяжёлый расчёт не должен останавливать мир.

## 8.1. Редактор формы и заточка: уточнение автора

Уточнение 2026-10-23 имеет приоритет над прежним ограничением редактора
одним продольным профилем. **[CANON]** Игрок почти свободно моделирует
форму внутри игры, буквально рисует её и задаёт длину, ширину, толщину
и общий размер. **[TENTATIVE]** Правит/выравнивает мышью.
Следующие конкретные инструменты — **[PROPOSAL]**, не утверждённый UI.

Предлагаемое взаимодействие:

1. Игрок рисует замкнутый контур, правит его точки и кривизну.
   Произвольная линия становится редактируемым контуром, а не выбирает
   ближайший готовый меч из каталога. Точные размеры можно вводить числом.
2. Контур получает объём. Виды сверху, сбоку и сечения позволяют менять
   локальную толщину: основание, середина, остриё могут отличаться.
   Один общий ползунок толщины недостаточен для целевого редактора.
3. Игрок вращает 3D-предпросмотр, двигает элементы формы, выравнивает
   выбранный участок. Предложить необязательную симметрию, привязки,
   сглаживание и отмену проектных правок. Помощники должны облегчать
   создание замысла, а не незаметно исправлять его эффективность.
4. В результате хранится проверяемое объёмное описание, из которого
   получаются визуальный mesh и расчётная геометрия. Форма, которую
   видит игрок, и форма, проверяемая сервером, должны соответствовать.

Не называть редактором свободной формы экран с тремя ползунками.
Одномерный расчёт из раздела 6 остаётся обязательным численным эталоном,
но не доказывает поддержку объёмного редактора. Для поддерживаемого
подмножества форм нужен проверенный перевод в расчётные сечения;
геометрию с поперечными обходами потока, отверстиями и ветвлениями
нельзя просто усреднить без сообщения пользователю. Такие проекты можно
сохранять, но до расширения решателя нельзя заявлять корректное литьё.
В отчёте явно различать завершённость редактора и области физического
решателя. Расширение топологии — следующий этап, не скрытая заглушка.

### Заточка как действие, а не готовый коэффициент

В прежней инструкции была формула уже заданных скосов, но не полноценное
взаимодействие. Предлагаемая операция: игрок выбирает зону кромки,
ориентацию/угол инструмента и проходом по поверхности снимает материал.
Предпросмотр показывает контакт и предполагаемый скос; после выполнения
сервер сохраняет новую геометрию. Возможность ручного управления проходом
и степень его автоматизации ещё не утверждены автором.

Предлагаемые входы: область обработки, траектория, ориентация инструмента,
разрешённая глубина/интенсивность и длительность. Не вычислять эффект
по числу кадров или сырых mousemove. Сервер проверяет доступный инструмент,
контакт, объём снятия и энергетические/временные ограничения выбранной
модели операции. Зависимость скорости снятия от материала и инструмента
остаётся отдельной задачей калибровки, не выдавать её за известный закон.

Базовое геометрическое условие:

```text
V_after = V_before minus V_removed
V_removed is a subset of actual existing material
mass_removed = integral(rho dV over V_removed)
```

Не допускай добавления металла заточкой, обработки пустого недолива или
отрицательной толщины. Предел разрешения сетки отдели от физической
геометрии кромки; для очень тонкой кромки потребуются локальные сечения
или отдельные геометрические параметры, согласованные с видимой формой.
Значение 0,1 мм в эталоне — один вход, не автоматическая награда за заточку.

Сохранять вдоль кромки её фактический угол, толщину/радиус окончания,
ширину скосов и асимметрию сторон. После операции пересчитать массу,
центр масс и инерцию. Связь этих величин с режущим действием/боем
пока не утверждена; не подставлять случайный бонус «острота +20%».
Производственная заточка не вводит затупление и износ в эксплуатации.

Проектную отмену отделить от уже совершённого физического снятия материала:
undo в чертеже не возвращает израсходованную массу в отливку. Для повторного
крафта чертёж хранит воспроизводимые требования обработки; по канону
игрок не обязан заново вручную рисовать каждый скос каждого экземпляра.

Дополнительная приёмка: два разных нарисованных контура сохраняются
разными; локальная правка толщины видна в объёме и расчёте; заточка одной
стороны создаёт асимметрию, уменьшает массу и сохраняется после переноса
предмета/рестарта. Клиентская картинка без изменения серверной геометрии
не считается реализацией операции.

## 9. Последовательность внедрения

1. **Inventory и базовые проверки.** Найди все ветки создания клинков,
   использования экземпляров и записи чертежей. Запиши baseline сборки,
   тестов и ограничения существующей станции. Не предполагай готовность
   подсистем по одному design-документу.
2. **Чистое ядро и fixture.** Реализуй геометрию, энтальпию, давление,
   перенос тепла/массы, события и численные проверки раздела 6.
   Никаких зависимостей ядра от UI/БД. Это промежуточный этап, не конец задачи.
3. **Данные и миграции.** Введи версии материалов, чертежи, сессии,
   результат экземпляра. Старые предметы сохраняют прежние значения;
   не изобретай для них утраченную геометрию. Старые трёхбайтовые чертежи
   преобразуй только по явно описанной legacy-схеме, без выдачи под видом
   нового физического опыта. Исторические миграции не переписывать.
4. **Серверный процесс.** Подключи физические ресурсы, станцию, команды,
   worker, checkpoints и транзакции. C90700 должен быть настоящим входным
   ресурсом тестового среза, а не переименованной золотой рудой. Получение
   бронзы из руды не является частью этого задания; допустим отдельный
   авторизованный dev-fixture, недоступный обычным игровым командам.
5. **Редактор и результат в мире.** Подключи полный пользовательский путь,
   правильный mesh, свойства и локальные дефекты, сохранение и повтор
   чертежа. Добавь обработку/сборку с учётом ограничений раздела 5.
6. **Снять обходы и проверить миграцию.** Старые `Design/CraftPlan`
   для заменённого семейства маршрутизируются в новый процесс либо
   явно перестают принимать старую форму команды. Не оставляй мгновенную
   выдачу через скрытый endpoint. Остальные рецепты/кулинарию не удалять
   как побочный эффект: перечисли их как ещё не мигрированные системы.
7. **Игровая проверка и отчёт.** Пройди обычную и узкую заливку клиентом,
   перенос/обмен результата и перезапуск; обнови документацию по факту.

На каждом этапе проект должен собираться. Изменения протокола проводить
совместно клиент+сервер, повысить версию и проверить отказ старого клиента.
Номер миграции выбирай после просмотра текущей папки, не из этого текста.

## 10. Что проверить перед сдачей

- Энергия нагрева, инверсия энтальпии и границы фаз; f=0/1 без NaN.
- K монотонно уменьшается при уменьшении f; при f=0,5 течение возможно;
  давление замыкается, Q неотрицателен, пустая ячейка не блокирует поток.
- Балансы массы/энергии с независимым учётом входа и теплоотдачи;
  объявленные допуски с абсолютной и относительной составляющими.
- Эталоны двух входов; уменьшение сетки и отдельно dt; d-чувствительность.
- Нулевая подача, прекращение заливки, недостаточная масса, охлаждение
  после остановки и полная заливка без сброса температурного поля.
- Невалидная геометрия отклоняется до списания; численный лимит не
  маскируется под физическую закупорку; сохранение/продолжение совпадает
  с непрерывным запуском в заданном допуске.
- Повтор/гонка команд, продажа зарезервированного сырья, две сессии на
  одни вещи, reconnect, падение до/после commit, полная сумка и рестарт:
  нет дюпа, потери собственности и двойного XP.
- Перенос/торговля/экипировка сохраняют геометрию и свойства, разные
  результаты не объединяются; legacy-вещи остаются читаемыми.
- В клиенте реально виден недолив, а обычный вход даёт полный профиль.

Применимые команды после проверки актуальной среды:

```sh
cargo fmt --all -- --check
cargo check --workspace
cargo test -p mortown-protocol
cargo test -p mortown-server --lib
cargo test -p mortown-server --test network
```

Последняя группа требует фактической тестовой инфраструктуры: изучи её
setup, используй отдельную БД и не печатай секреты. Если добавлен crate,
проверь его отдельно. Не объявляй непроведённую ручную проверку успешной.

В итоговом отчёте: изменённые модули/миграции, реально работающий игровой
путь, результаты численных и сетевых проверок, время/память расчёта,
оставшиеся ограничения. Отдельно указать, решена ли подпитка физически
или используется явно обозначенное идеальное условие.
Не заявлять готовую универсальную физику крафта после одного сценария.
